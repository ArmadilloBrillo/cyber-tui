# 44 — Inline Images Everywhere

## Overview

The `inlineImages` setting previously only rendered images inline in Feed and Post Detail. This extends the same feature to every other screen that shows post or message content, plus Profile:

- **Search, Topics, Guilds** (post lists): these already rendered posts through the same `RenderPost`/`renderPostBody` pipeline Feed uses, but hard-coded `inlineImagesEnabled=false`. They now pass their own gated flag through, matching Feed exactly — including the "cap to the first eligible image" behavior list views already had.
- **C-Mail, cIRC**: a message's image — its `ImageUrl`/`GifUrl` attachment field, or the first image-looking URL typed into the body (`chatInlineImageURL()`, `shared.go`) — renders inline in a reserved band appended right after that message. The message's own attachment badge/URL text is suppressed for the part the image now shows (`sanitizeChatMessageForInlineImage()`, `shared.go`) so nothing sits redundantly behind the image; a URL embedded alongside other text is left alone (known scope limit — see that function's doc comment). `infoTabView`'s "Picture"/"img" rows are unrelated to this and untouched.
- **Profile**: `ProfilePictureUrl` renders inline between the username line and the followers/following count line; `WebsiteImageUrl` renders inline below all tab content instead — both use a Profile-specific, smaller row budget (`profileImageMaxRows`) than Feed/PostDetail/chat, since a typical avatar doesn't need the full 8-row budget those screens reserve. `infoTabView`'s "Picture"/"img" text rows are untouched — the URL stays visible where it already was.

None of the underlying fetch/encode/cache/placement machinery changed (`App.syncInlineImages`, `fetchInlineImageCmd`, the inline image cache, `syncKittyPlacements`, `injectInlineImages`). Each screen only adds: a way to find eligible image URLs in its own content, and a `VisibleInlineImages() []screens.InlineImageSlot` method reporting their current on-screen position — the same "where, if anywhere" query contract Feed/PostDetail already established.

## Search / Topics / Guilds

`RenderPost` (`render.go`) now takes an `inlineImagesEnabled bool` and returns `(string, []postImageSlot)` instead of discarding the slot data. Each screen tracks slots parallel to its row/offset list (`SearchModel.rowImages`, `TopicsModel.postImages`, `GuildsModel.postImages`) and exposes `VisibleInlineImages()` the same way `FeedModel` does for its list view. Guilds and Topics also participate in Miller's compact list+detail split, so they additionally expose `VisibleDetailInlineImages(width, height)` for the post card in the reading pane — replies in that pane are still rendered via plain `markdown.Render` and aren't inline-image-aware.

Wired into `App.activeInlineImageSlots()`/`activeSelectionKey()` (new cases for `screenSearch`/`screenTopics`/`screenGuilds`) and `MillerLayout.InlineImageSlots()` (Guilds/Topics extend the existing compact-renderer branch; Search gets a plain-content-pane case alongside Post Detail).

## C-Mail / cIRC

`renderChatMessagesWithSelection`/`renderCircMessagesWithSelection` (`render.go`) — the functions that actually build the displayed viewport content — take an `inlineImagesEnabled bool` and return a fourth value, `imgSlots [][]postImageSlot`, 1:1 with the message list. When a message has an eligible image, that message is rendered from a `sanitizeChatMessageForInlineImage()` copy (attachment badge / URL-only body cleared) rather than the original, then a reserved band is appended after its rendered lines. `CMailModel`/`ChatroomsModel` store the slots as `msgImages` alongside the existing `msgOffsets`/`msgHeights`, and `VisibleInlineImages()` walks it the same way `FeedModel.VisibleInlineImages` does.

cIRC's `ChatroomsModel.VisibleInlineImages()` computes each slot's `ColIndent` from `circMessageTextIndent()` (`render.go`) — the same username-length-derived hanging indent `renderCircMessagesStyled`/`renderActionLine` wrap body text to — so the image's left edge lines up with where that message's own text starts, not a generic fixed guess. C-Mail's bordered "bubble" layout has no equivalent per-username indent, so its `ColIndent` stays a fixed small value.

Muted senders and system notices never get a band (their rendered block contributes nothing, so there's nothing to append after).

**Dynamic band resize** (`chatImageBandRows()`, `render.go`): a chat image's reserved band starts at a fixed fallback-max size (1 leading spacer + `inlineImageEncodeMaxRows`, no trailing spacer — the fallback is safe because it *is* the `maxRows` bound passed to the encoder, so the image can never render taller than it). The image encoders (`imgview.EncodeKitty`/`EncodeITerm2`/`EncodeSixel`) already compute the image's real fitted row count as part of encoding; `App.fetchInlineImageCmd` now captures that instead of discarding it, and `App.recordInlineImageRealRows` routes it (by `inlineImageFetchedMsg.slotKey`'s `"cmailmsg:"`/`"circmsg:"` prefix) to `CMailModel`/`ChatroomsModel.SetImageRealRows(key, rows)`, which caches it in `m.imageRealRows` and calls `refreshMessages()` to reflow — shrinking that message's band down to its real size (still no trailing spacer) and moving every later message up to match. A no-op if the row count didn't change, so a stable cache hit never triggers a redundant re-render.

That real row count is only as accurate as `imgview.TerminalCellPixelSize`'s cell-size measurement feeding into the Sixel/Kitty/iTerm2 fit-box math (`internal/ui/imgview/scale.go`'s `fitBox`/`fitRows`). On Windows this used to be an always-`ok=false` stub (`cellsize_windows.go`), forcing every image — inline or fullscreen — through a hardcoded guessed cell size regardless of the real terminal font, which showed up as a small but consistent residual gap under Sixel images even after the dynamic-resize fix above. `cellsize_windows.go` now calls the real Win32 `GetCurrentConsoleFontEx` API (via `golang.org/x/sys/windows`, already a direct dependency — no new one added) to get the console host's actual current font cell size, falling back exactly as before (`ok=false`) on any failure. Caveat documented on the function itself: terminals that run over ConPTY (Windows Terminal, mintty, etc.) aren't guaranteed to have this reflect their real rendered font pixel size, so this narrows the imprecision rather than eliminating it outright for every Windows terminal.

**Sticky-bottom on reflow**: opening a room/conversation renders every image band at the fallback-max size (nothing's been fetched yet) and calls `viewport.GotoBottom()` — correct for that instant, but as each image's real size arrives and `SetImageRealRows` shrinks its band, the content keeps getting shorter under a `YOffset` that never moves, so the view would settle above the true bottom instead of following it down. `SetImageRealRows` (both `CMailModel` and `ChatroomsModel`) now captures `viewport.AtBottom()` before the reflow and re-calls `GotoBottom()` after it if it was already there — never forcing the view down if the user had scrolled up to read history.

**Sticky-bottom generalized to every live message, plus unread while scrolled up**: the same "only follow if already caught up" principle now applies to `AppendMessage` itself (both `CMailModel` and `ChatroomsModel`), not just the image-band reflow case — a new message, image or not, never auto-scrolls a view that's currently scrolled up. Alongside that, the unread tab badge (`ChatroomsModel.unreadCount` / C-Mail's per-conversation `UnreadCount` summed by `TotalUnread()`) used to only increment while the screen wasn't focused at all; the `roomReceivedMsg`/`dmReceivedMsg` handlers now also bump it while focused if `!viewport.AtBottom()` — you're on the tab, but not looking at the newest message. Both screens' outer `Update()` (the single wrapper both already had around `updateInner()`) clears the badge the moment the view is back at the bottom while focused, regardless of what scrolled it there (Esc from browsing, paging past the newest message, sticky-scroll itself, or a plain scroll) — one choke point instead of hunting down every individual path.

**Known unrelated issue found along the way**: `CMailModel`'s `tea.WindowSizeMsg` handler computes its detail viewport height (`msg.Height - theme.ChromeHeight - cmailDetailChrome`) with no floor, unlike `ChatroomsModel.viewportHeight()`'s `if h < 1 { h = 1 }` clamp — an unrealistically short terminal can drive it negative and panic inside bubbles' viewport. Not hit by any real terminal size, surfaced only by an overly-aggressive test height during this work, and left unfixed as out of scope for the inline-images feature.

## Profile

Profile's header isn't viewport-scrolled — it's a fixed block at the top of `View()`. `ProfilePictureUrl`'s band is a fixed row (row 0 is always the username line), reserved directly in `headerParts`. `WebsiteImageUrl`'s band renders after all tab content instead, so its row isn't fixed — it depends on the active tab and how much data is loaded. `viewBodyBeforeWebsiteBand()` builds everything up to (not including) that band; both `View()` and `VisibleInlineImages()` call it (the latter just to measure `lipgloss.Height(...)`) so the reported row always matches what's actually on screen — the same "recompute fresh each call" approach `FeedModel.VisibleDetailInlineImages` uses for the same reason (a value-receiver `View()` can't persist state back onto the model). Both bands use `profileImageMaxRows`/`profileImageBandRows`/`profileImageEncodeMaxRows` — smaller than the shared Feed/PostDetail/chat constants, since Profile only ever shows one or two small avatar-ish images and the full 8-row budget left visible slack around a typical picture. A band that wouldn't fully fit within the screen's available height is omitted rather than reported at a row that's actually been clipped by `View()`'s own `MaxHeight`.

Profile has no post/reply-style selection, so `App.activeSelectionKey()` returns `""` for it — `selectionTouchesSlot` already treats an empty id as "never touches."
